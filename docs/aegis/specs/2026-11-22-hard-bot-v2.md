# hard Bot 強化（v0.4.6）：審查結論、優化項目與驗收

日期：2026-11-22。狀態：**spec 草案；尚未實作，沒有跑任何新的 bench。**

前置閱讀：`docs/SPEC.md` §4.9、§8.3；`docs/aegis/specs/2026-11-07-hard-bot.md`（hard 的資訊邊界、不變式 H1–H9 與量測方法）；`docs/aegis/specs/2026-11-01-bot-opponents.md`。本文件只處理基本版（`base-2025`、`base-paired-2025`）的 `hard`；權威需求仍以 SPEC 為準。

## 1. 目標與範圍

重新審視基本版人機策略，找出 `hard` 可以變強的地方，並定出實作順序與驗收方法。

範圍內：

- `packages/bots/src/hard/` 內的策略改動，以及 hard 專屬的 tracker 用法。
- `packages/bots/bench/` 的小幅工具改動（可選的 `--seed`），不影響 bot 行為。
- 與本次審查相關的文件落差（§6）。

範圍外：

- standard、easy 的任何行為變更（見 V1）。
- 擴充版 profile 的 hard（H9 仍然有效）。
- 協定、伺服器與前端。

## 3. 審查方法

2026-11-22 以兩個模型各自獨立審查（Gemini 4 Neon、GPT-6.2 Sol），先審整體，再依範圍交叉審查 `hard/`，三個範圍各有兩份報告：

- 開局、經濟、強盜與騎士、發展卡、手牌過多；
- 交易與對手模型、終盤搜尋、計牌與信念、威脅評估；
- 整體審計與難度階梯。

審查者只讀程式碼與文件，**沒有跑 bench**；下表「判定」是兩份報告的交集，兩邊有出入的標為「分歧」。行號以 `ffca6dc` 為準，函式名稱比行號可靠。

## 5. 優化項目

全部只改 `hard/`（或 hard 專屬的 tracker 用法）。「效益」是審查者的預期，**不是量測值**；每項都要靠 §7 的消融證明有效才保留。

### O-A　對手模型補公開 `hints`

- **現象**：E13。`acceptOdds` 與 `rivalBenefit` 依賴失真的對手經濟。
- **改法**：新增 `rivalHints`，由公開盤面與 `isFreeSpot` 推算對手的 `bankRates`、`legalSettlements`、`legalRoads`、`legalCities`，在 `buildRivalModel` 算一次並注入 `viewAs`。`rivalBenefit` 掃所有即時計畫（含差 1 條的 `longestRoad`），不只看 `plans[0]`。降級（`worlds = []` 且對手有牌）時補一個四捨五入的期望世界，不直接關閉開價。
- **效益／風險**：高／極低。純公開資訊，耗時 < 0.02 ms。

### O-B　指名開價與安全結算

- **現象**：E14、E15。
- **改法**：新增 `hardOwnOfferStep` 取代 `hard/action.ts` 對 `ownOfferStep` 的直接呼叫。過濾計牌確定付不起的對手與高威脅領先者（除非結算後 `winningLine` 致勝）。`hardProposal` 對「接受率 × 自身收益 − 幫助威脅」最高的對手發 `to: rivalId`，並加入混色 2:1。維持 `MAX_OFFERS_PER_WINDOW = 2` 與不看 `to` 的 `sameTerms` 去重。
- **效益／風險**：高／低到中。依賴 O-A、O-H。真人的體感要同時看開價頻率。

### O-C　`hardHandRelief`

- **現象**：E6。8 張牌差 1 礦蓋城時，現況會買發展卡而拆城，但留著手牌就算擲 7 棄 4 張也能保住主計畫。
- **改法**：新增 `hardHandRelief`：先找不傷 `plans[0].cost` 的銀行換匯（沿用 `bankTradesThisTurn` 防來回），再找不傷主計畫的建造；只有「棄半後會被迫丟主計畫的牌」或「期望棄牌損失大於拆計畫損失」才拆。擲 7 機率用 `1 - (5/6)^rolls`，`rolls` 依人數與 paired 的無骰窗計算。同時把 `hardDiscard` 前三案去重。
- **效益／風險**：高／低。O(5) 運算。

### O-D　發展卡出牌時機

- **現象**：E7、E8。
- **改法**：
  - `hardKnightDecision`：已穩握最大騎士團且不需解封、不能奪獎時，留末張；`preroll` 若持有本回合會用到的壟斷／豐收，且騎士不是致勝或解封，延到 `action`。
  - `roadBuilding`：只在致勝、搶點、守或奪最長路時打，並試第二步。
  - `yearOfPlenty`：逐資源驗證銀行可用量與缺口（`view.bank` 只在豐收視窗可見，須守 H2）。
  - 非致勝的壟斷排在立即得分的建造之後。
- **效益／風險**：中到高／低。

### O-E　開局

- **現象**：E2–E5。3 人局未達標的主要手段。
- **改法**：
  - `openingValue` 加入 `secondVertex` 的起始手牌分，`share` 依地塊數（`landHexCount / 19`）還原尺度。
  - `settlementChoice` 對前 4–6 名候選續跑 `rivalsAfter`，R2 實放時把 `taken` 帶回 `expansionSpots`。
  - `roadChoice` 刪除 `visit(far, 1)`，補深度 3 與朝另一座己方聚落連通的加分。
  - 分 3 / 4 / 5–6 人建模；是否重訓權重要先用 `survey` 拆解 3 人局的落後來源（開局或中盤），再決定。
- **效益／風險**：高／中。要防過擬合（V5）。候選上限固定，守 H5 尾延遲。

### O-F　經濟：並行 ETA 與港口

- **現象**：E11、E12。
- **改法**：`hardEconomyOf` 的 ETA 改成直產資源並行（取最慢者），只有超額資源才按各自匯率換缺口；港口價值以新舊匯率的 ETA 差估算，取代固定加值，並對已有港口去重；搶點距離折價依對手實際路程放寬或收緊；騎士權重依與最大騎士團的差距調整。
- **效益／風險**：高／中。會改變全域排序，必須逐項消融（先 ETA，再港口，再搶點）。

### O-G　終盤搜尋納入發展卡

- **現象**：E16。
- **改法**：`endgame.expand` 加入已持有且可打的 `knight`（奪最大騎士團）、`yearOfPlenty`、`roadBuilding`，以及依 `Σ opp.min[r]` 取下界的確定 `monopoly`（不假設知道真實手牌）；銀行分支展開所有 `hand[g] - cost[g] ≥ rate[g]` 的 `give`；節點與 `keyOf` 帶 `devCardPlayed`。`winningLine` 移到 `hardDevCardDecision` 之前，`pendingDecision` 對 `yearOfPlenty`、`freeRoads` 沿用同一套搜尋選續步。節點上限 600–800，維持決定性排序。
- **效益／風險**：中到高／H5 風險中到高。最後做，先單獨驗證效能。

### O-H　VP 威脅與舊卡信念

- **現象**：E17、以及 `hard/turn.ts` 的 `threat` 只看期望分數的階梯。
- **改法**：在 `hard/` 內由 unseen VP pool 算「達到威脅門檻」的機率，取代期望分數；久持舊卡以存活率倍率上調隱藏 VP，並加「上回合結束未勝」的邏輯上界。存活率 `h`（審查者建議約 0.25）**未校準**，要用實局校準。同分領先者以產能破平。**不改 `tracker.ts`**，避免動到 `tracker.test.ts` 鎖定的式子。
- **效益／風險**：中／低到中。小樣本先驗要校準。

### O-I　強盜瓶頸與終盤偷牌

- **現象**：E9、E10。
- **改法**：`robberScores` 對「佔對手某資源 ≥ 50% 產能」的格子與對手 2:1 港加權；`stealValue` 對接近勝利者加終盤權重。`STEAL_THREAT` 作為消融旋鈕，不獨立調整（E9 分歧）。
- **效益／風險**：中／低。

### O-J　`hardDiscard` 保護換匯區塊

- **改法**：`keepValue` 加入完整換匯區塊的加分，權重依 `plan.score` 正規化。
- **效益／風險**：低到中／低。次要，放最後。

## 6. 既有文件的落差（本 spec 不改既有文件）

1. hard-bot H-I3 說 standard／easy 不受 `view.events` 影響，但 `bankTradesThisTurn` 讀它（E18）。實作切片補一個「有／無同回合 `trade.bank` 事件」的測試或更正文字，**不改行為**。
2. hard-bot §5 描述「指名開價」與實作不符（E14）；O-B 完成後一併更新。
3. `docs/FIDELITY.md` 沒有基本版 bot 的證據列；實作完成時補上，列出對應測試檔。
4. `bench/survey-records.ts` 尚不支援 `hard`；需要拆解 3 人局落後來源時補上。

## 7. 量測與驗收

- **工具**：`bench/run.ts`（`[games] [filter] --profile`，逐局輪換 `focus` 座位）。種子目前固定從 `10000` 起，切片 S0 加可選的 `--seed`，才能做 V5 的 holdout；這不是 bot 行為，不違反 V1。
- **基線**：實作前先用未改動的 hard 在相同設定與種子跑出基準表，記錄到 `docs/aegis/work/` 的實作紀錄。
- **小樣本篩選**：3 人與 4 人 `1 hard vs standard`，各 200 局（標準誤約 3.5 個百分點）。小樣本只能篩行為與效能，不能驗收 H6。
- **合併驗證**：3／4 人各 500 局、5／6 人各 300 局，另加全 hard 的壓測，以及「新 hard 對舊 hard」。
- **最終驗收**：`50000` 起的 holdout，3 人局至少 1,000 局。
- **閘門**：拒絕、卡死、看門狗、保底皆為 0；平均決策 ≤ 5 ms、最大 ≤ 50 ms；`offers/game` 與 `settled/game` 不明顯增加；`test/hard.test.ts`、`test/golden-base.test.ts`、`test/fair.test.ts` 通過。
- **消融**：每項單獨開關比較；經濟（O-F）內再拆 ETA、港口、搶點。
- **機器限制**：測試檔單獨跑並加 `--testTimeout 120000`；逾時先單獨重跑或 `--maxWorkers 2`，再判定是否真的失敗。

## 9. 風險與未決

1. **3 人局能否單靠啟發式過 50%**：hard-bot §13.4 曾嘗試多組開局模型，仍停在 44–47.5%。O-A 到 O-D 是結構性修復，O-E、O-F 才是主要手段；合計是否足夠要靠實測。若仍差 1 個百分點，可能需要更細的回合內前瞻，那是另案。
2. **對手假設**：`setup`、`trade` 假設對手照 standard 的公式決策；對全 hard 或真人的增益可能小於對 standard 的 bench。
3. **真人體感**：指名開價與放寬領先者交易會改變節奏，要同時看勝率與開價頻率。
4. **權重過擬合**：O-E、O-F、O-H、O-I 的係數要用 holdout 驗證。
5. **終盤搜尋的尾延遲**：O-G 的分支變多，可能逼近 H5 的 50 ms 上限；先設節點上限並單獨驗證。
6. **release 分支前進**：以合併 `release/v0.4.6` 的方式跟上，不 rebase 已推送的分支（RELEASING.md）。
