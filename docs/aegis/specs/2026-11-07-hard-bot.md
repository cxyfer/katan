# 困難電腦（hard Bot）：規格與實作計畫

日期：2026-11-07。狀態：**PR 1（完整歷史＋計牌模組）、PR 2（hard 策略，量測見 §13）、PR 3（開放 `hard` 等級）都已開 draft。**

前置閱讀：`docs/SPEC.md` §4.9、§8.3；`docs/aegis/specs/2026-11-01-bot-opponents.md`（Bot 合約、不變式 I1–I9、BotDriver）。本文件是 hard 難度的設計與交付紀錄，權威需求仍以 SPEC 為準。相關 issue：#137（銀行精確存量會洩漏棄牌內容）。

## 1. 目標與範圍

在基本版（`base-2025`、`base-paired-2025`）新增 `hard` 難度：記性完美、會計牌，並且有前瞻規劃。

範圍內：

- 所有難度的 Bot 都會拿到自己座位投影過的**完整事件歷史**。目前伺服器只傳最近 40 筆，引擎快照最多保留 200 筆，而一局有 430–1000 筆事件。
- 歷史事件 API（`GET /api/games/:gameId/events`）改成與快照、推送相同的投影：只遮私有欄位，不再整筆省略事件。
- 計牌模組：只根據投影後的事件，推算每位對手的手牌分布、發展卡池與隱藏分數。
- hard 策略：開局前瞻、回合內搜尋、局面評估、依計牌結果決定強盜、偷牌、壟斷與交易、威脅與終盤判斷。
- 協定、伺服器、前端開放 `hard` 等級，並修訂 SPEC §4.9。

範圍外：

- 擴充版 profile 的 hard。hard 只支援沒有 rules module 的 profile（`hardSupports`）；這些 profile 不提供 hard：伺服器拒絕加入、拒絕把有 hard 的房間改過去、開局時擋下（`blocker.botLevelUnsupported`），大廳不列出並說明原因。策略萬一在這種 profile 被呼叫，交給 standard。
- 主執行緒上的蒙地卡羅整局推演（見 §7）、worker thread。
- Bot 的反報價、聊天。
- #137 的修正方式（另案）。

## 2. 已定案決策

| # | 決策 | 定案 | 理由 |
|---|---|---|---|
| H1 | 資訊 | 每個難度都拿同一份完整投影歷史；只有 hard 使用 | SPEC §4.9「難度只改變策略品質，不改變能取得的資訊」維持成立；玩家可以從事件 API 分頁讀到同一份歷史 |
| H2 | 棄牌身分 | 維持私有：計牌只用「誰棄了幾張」，**不讀 `view.bank`** | 正常介面看不到銀行存量（只有豐收之年的選牌視窗會顯示）；比對前後快照的銀行存量屬於 #137 的洩漏，hard 不得利用 |
| H3 | 改進範圍 | 只放進 hard；standard／easy 行為凍結 | 難度之間的差距清楚；golden 測試（`test/golden/base-v040.json`）守住凍結 |
| H4 | 運算方式 | 主執行緒上的啟發式＋回合內搜尋＋計牌；搜尋以節點數設上限，不以時間 | 決策必須決定性（I6）；整局推演一次就要 140–350 ms（§7） |
| H5 | 效能預算 | hard 每次決策平均 ≤ 5 ms、最大 ≤ 50 ms（bench 記錄平均與最大） | 伺服器是單執行緒，Bot 決策會擋住其他牌局的事件處理 |
| H6 | 強度目標 | bench：4 人局 1 hard 對 3 standard 勝率 ≥ 40%（公平份額 25%）；3 人局 1 hard 對 2 standard ≥ 50%（33.3%）；5／6 人局至少公平份額的 1.5 倍；拒絕、卡死、保底皆為 0 | 使用者同意，但要兼顧效能 |
| H7 | 分支 | 系列 PR 疊在 `release/v0.4.1` 上，先開 draft PR 指向它；v0.4.1 合回 master 後改指向 master | release 分支已重構 Bot（`src/base/*`、`modules/`、harness），以 master 為基準會大量衝突 |
| H8 | 事件 API | 併入 PR 1 修正 | 「Bot 拿到的歷史等於玩家可分頁讀到的歷史」這個前提才成立 |
| H9 | 擴充版的 hard | 只在基本版提供：伺服器拒絕、大廳不列出並說明原因（2026-11-07 使用者選擇） | 擴充版的 hard 實際上是 standard，標示成「困難」會誤導 |

## 3. 資訊邊界

hard 可以使用的資訊，全部來自自己座位的 `GameView`（含 `events` 與 `hints`）、公開拓樸與規則常數：

| 來源 | hard 的用法 |
|---|---|
| 起始資源、擲骰產出、建造（含是否免費）、銀行／港口交易、完成的國內交易、豐收之年選的資源 | 精確加減對手手牌 |
| 壟斷（`taken` 只列出被拿走的玩家） | 被拿走的人該資源原本恰好是那個張數；沒列出的人原本是 0 張 |
| 偷牌：誰偷了誰 | 自己是小偷或受害者時知道牌面；否則把「受害者少一張、小偷多一張」分成各種可能 |
| 棄牌：誰棄了幾張 | 依超幾何分布展開各種可能；不讀銀行存量 |
| 公開的手牌張數、發展卡張數、已打出的騎士數 | 檢查推算是否一致、估算隱藏分數 |
| 牌庫組成（profile 的 `devDeck`）、牌庫剩餘張數 | 算出尚未現身的發展卡分布 |

hard 不得使用：

- 銀行存量的前後差（#137）；
- 其他座位的私有事件欄位（投影已經濾掉）；
- 任何 `GameState`。

SPEC §8.3 寫的「v1 不提供對手手牌推論助手」是針對玩家介面。hard 的推論只在策略內部使用，Bot 不聊天，也不會把推論結果傳給任何座位。

## 4. 現況評估（2026-11-07）

bench（每種設定 100 局，種子從 10000 起，master `0efd30c`）：

| 設定 | standard 勝率 | 公平份額 |
|---|---|---|
| 3 人：1 standard 對 2 easy | 39% | 33.3% |
| 4 人：1 standard 對 3 easy | 43% | 25% |
| 5／6 人：1 standard 對其餘 easy | 31%／31% | 20%／16.7% |

700 局全部正常結束，沒有拒絕或卡死。行動階段的一次決策約 0.07 ms。

standard 是每步只看眼前的無狀態啟發式。hard 要補強的地方（依預期影響排序；函式位置以 release 分支為準）：

1. **開局放置**（`src/base/setup.ts` 的 `setupSpotScore`）：只算點數、資源種類與港口。第二座缺木或缺磚各扣 3 分，等於不看盤面一律走鋪路擴張。hard：模擬蛇形順序中對手的選點並聯合規劃兩座；考慮數字分散、擴張潛力，依盤面選擴張或城市路線。
2. **回合內規劃**（`src/heuristic.ts` 的 `buildDecision`、`src/trade.ts` 的 `bankTradeToward`）：一次只看下一步，只有「換完這回合就能蓋」才交易。hard：搜尋本回合的交易、建造、發展卡序列，評估回合結束時的局面，含 7 點風險。
3. **局面評估**（`src/economy.ts` 的 `baseEconomyOf`）：`價值 / (1 + 預估輪數)`，權重不分階段；搶點只用距離打折，不看對手是否更快到達；最長道路只在差 1–2 條時才追，也不防守；發展卡價值固定。
4. **強盜與偷牌**（`src/base/robber.ts` 的 `robberCandidates`、`src/heuristic.ts` 的 `stealVictim`）：只看點數、領先程度與手牌張數。hard 依計牌結果，計算偷到的牌對自己的期望價值與對領先者的封鎖價值。
5. **壟斷**（`monopolyChoice`）：用產能比例估計；hard 直接用計牌結果。
6. **交易**（`src/trade.ts` 的 `acceptMargin`、`offerGain`、`proposeOffer`）：只看公開分數與自己的效用，只對全桌開價。hard 指名開價給確定有牌、又不構成威脅的玩家，並拒絕會讓對方立刻完成城市或聚落的交易。
7. **威脅與終盤**：沒有估算隱藏分數，除了騎士之外也不搜尋「這回合能否獲勝」。
8. **發展卡時機**（`knightDecision`、`devCardDecision`）：道路建設只要有合法道路就打，騎士只在少數條件下才打。
9. **棄牌與 7 點風險**（`discardDecision`、`handRelief`）：只保留第一順位計畫的牌，沒有計算擲出 7 的機率。

### 5.1 BotDriver 的歷史快取

- `GameRuntime.history: GameEvent[]`：持久化事件的純快取（含私有欄位），`forget()` 時一起丟棄。重啟後會從資料庫重新載入，「排程器不保存決策狀態」仍然成立。
- 每次 `evaluate` 讀到 `state` 後，從快取最後一筆的 seq 之後，每頁 500 筆向資料庫補齊到 `state.seq`，只收 `seq ≤ state.seq` 的事件。如果補完不連續或沒有補到 `state.seq`，丟掉快取，下次從頭載入；本次照樣決策，計牌模組會因為歷史不完整而降級。
- 投影仍透過 `projectGame` 的 `projectEvent` 遮掉私有欄位，與玩家的快照完全一致。

### 5.2 事件 API

`GameCoordinator.events` 改為 `events.map((event) => projectEvent(event, playerId))`：

- 旁觀者照樣看得到「誰偷了誰」「誰買了發展卡」，但看不到牌面；
- 收件人看得到私有欄位，回應中不含 `private` 物件。

這與快照、推送的行為相同，因此不會多揭露任何資訊。三個隱私測試原本寫死「旁觀者在歷史中看不到該事件」，改為「事件存在，但沒有私有欄位」。

## 6. 計牌模組（`src/tracker.ts`）

```ts
export function trackTable(view: GameView, selfId: string): TableBelief;

interface TableBelief {
  complete: boolean;                      // 歷史從 seq 1 連續到 view.seq，且 profile 沒有 rules module
  hands: Record<string, HandBelief>;      // 只有對手
  dev: DevCardBelief;
}
interface HandBelief {
  playerId: string;
  size: number;                           // 推算的張數，應等於公開 handSize
  worlds: { hand: Record<Resource, number>; p: number }[];  // 依機率遞減，同機率依 key 排序
  expected: Record<Resource, number>;
  min: Record<Resource, number>;          // 每種可能都至少有的張數（確定持有）
  max: Record<Resource, number>;
  exact: boolean;                         // 只剩一種可能
  consistent: boolean;                    // false 時 worlds 為空，expected 改用產能比例估計
}
interface DevCardBelief {
  unseen: Record<DevCardType, number>;    // 牌庫加上對手手上未打出的牌
  unseenTotal: number;
  players: Record<string, { held: number; bought: number; played: Partial<Record<DevCardType, number>>; victoryPoints: number }>;
}
```

演算法：

- 每位對手各自維護一組「可能手牌 → 機率」的集合，相同手牌合併。事件依 seq 順序處理（處理方式見 §3 的表），付出成本、壟斷時把不可能的手牌刪掉並重新正規化。
- **不知牌面的偷牌**：受害者的每種可能手牌依張數比例展開「少一張某資源」；被偷資源的分布再套到小偷身上，展開「多一張某資源」。小偷與受害者之間的相關性不保留，這是刻意的近似，但真實手牌仍一定留在可能集合中。
- **棄牌**：依多變量超幾何分布，展開所有「棄掉 n 張」的子集合。
- **上限**：每位對手最多保留 2000 種可能，超過時刪掉機率最低者（同機率依 key）。如果後續事件把所有可能都刪光（截斷刪到真實手牌，或歷史本身不一致），該玩家改標 `consistent: false`，只追蹤張數，分布改用產能比例估計。
- **完整性**：第一筆不是 seq 1、seq 不連續、最後一筆不是 `view.seq`、profile 有 rules module，或推算張數不等於公開 `handSize`，都會標成 `complete: false`。hard 遇到不完整時退回 standard 的估計方式。
- **發展卡**：`unseen` = profile 的牌庫 − 自己持有與打出的牌 − 對手打出的牌（騎士用公開的 `playedKnights`，其他從事件取得）。對手的隱藏分數期望值 = 持有張數 × `unseen.victoryPoint / unseenTotal`。
- **純函式**：只讀 `view`（不讀 `view.bank`）、不保留狀態、不使用亂數。實測每次決策重播完整歷史只要 0.3–0.5 ms（§11），所以不做跨呼叫快取。

## 7. 效能預算與量測

量測環境：4 人局、全部 standard 對局中的 146 個中盤狀態（2026-11-07）。

| 基本操作 | 單次成本 |
|---|---|
| standard 在行動階段的一次決策 | 0.07 ms |
| `actionHints`／`projectGame`＋hints | 0.03／0.035 ms |
| 引擎 `applyCommand`（深拷貝整份狀態，含 log 與統計） | 0.61 ms |
| Bot 自建輕量模型的複製（手牌、銀行、棋子） | 0.0005 ms |

以引擎展開本回合的交易與建造（重複局面只算一次）：

| 深度 | 平均節點 | 最大節點 | 平均耗時 | 最大耗時 |
|---|---|---|---|---|
| 1 | 4 | 17 | 3.4 ms | 18 ms |
| 2 | 14 | 146 | 15 ms | 177 ms |
| 3 | 31 | 650 | 45 ms | 1.2 s |
| 4 | 59 | 2231 | 107 ms | 4.6 s |
| 6 | 121 | 7665 | 307 ms | 23 s |

整局推演（所有座位用 standard）：1 輪 10.5 ms、2 輪 22.8 ms、到終局 159 ms。

結論：

- hard 的回合內搜尋必須用輕量模型，不能用引擎展開節點。
- 交易只往計畫需要的資源換、道路只朝目標方向鋪，用來修剪分支；節點上限約 800–1000，預估平均 2–5 ms、最壞 40–50 ms。
- 下一輪骰子直接算期望值，不實際模擬。
- 不在主執行緒上做蒙地卡羅推演。
- 計牌模組平均 0.3–0.5 ms、最大 4.3 ms（§11）。

## 8. 不變式（在 I1–I9 之外新增）

| ID | 不變式 | 守護方式 |
|---|---|---|
| H-I1 | 計牌模組只讀 `view`，不讀 `view.bank`；隱藏資訊不同但投影相同時，結果相同 | 公平性測試：改動銀行存量、對手牌面、牌庫順序，結果不變 |

| H-I4 | hard 的搜尋以節點數設上限；同一 view 與 context 得到同一指令 | B-POLICY 決定性測試 |
| H-I5 | 伺服器投影給 Bot 的歷史與該座位從事件 API 讀到的相同 | server 測試 |

## 12. 風險

1. 偷牌與棄牌讓可能手牌數量膨脹：靠相同手牌合併、上限與降級處理；T-SOUND 監測降級比例。
2. 獨立近似會丟掉小偷與受害者之間的相關性：不影響正確性（真實手牌仍在可能集合中），只是分布較寬。
3. 歷史快取的記憶體：每局約 1000 筆事件，只存在有 Bot 的進行中牌局，結束或遺忘時釋放。
4. release 分支在 PR 期間可能繼續前進：分支以合併 `release/v0.4.1` 的方式跟上，不 rebase 已推送的分支。

## 13. hard 策略（PR 2）

### 13.1 決策點

hard 的流程與 standard 相同：每次只決定一個指令，不保留跨呼叫狀態。各決策點換成下表的版本，其餘沿用 standard（計畫的下一步、銀行交易、手牌過多時的消化、豐收之年、道路建設、免費道路）。有 rules module 的 profile 整個交給 standard。

| 決策點 | hard 的做法 | 檔案 |
|---|---|---|
| 開局放置 | 從自我對局學到的 logistic 模型評分（§13.3）。第一座對前 10 名候選點，以 standard 的開局公式模擬對手在兩座之間的選點，再挑自己最好的第二座；兩座都計入「搶走對手的好點」；道路朝模擬後還會留下的空點鋪 | `setup.ts` |
| 強盜、偷牌 | 封鎖的點數依估計分數（含隱藏分的期望）加權；偷牌依計牌結果估計偷到的牌對自己的價值 | `robber.ts` |
| 騎士 | standard 的時機之外，只要還追得上最大騎士團就打 | `robber.ts` |
| 壟斷 | 依計牌結果的期望張數 | `cards.ts` |
| 棄牌 | 列舉所有棄法，保留對前三個計畫加權效用最高的手牌 | `cards.ts` |
| 國內交易 | 以計牌模組的可能手牌加上 standard 的估值方式，推估每位對手接受報價的機率；在銀行交易之前開價。回應報價時，若對方會因此湊齊主要計畫，依計畫價值與威脅度提高門檻 | `trade.ts` |
| 計畫估值 | 最長道路差 1–4 條就列為計畫，自己持有時防守；發展卡價值為 standard 的 1.3 倍，並依未現身牌池調整 | `economy.ts` |
| 終盤 | 離勝利 3 分以內時，在輕量局面上廣度優先搜尋本回合的建造與銀行交易（節點上限 600），找到這回合就能贏的序列就照做 | `endgame.ts` |

hard 只讀自己座位的 `GameView`。對手模型用的是公開盤面與計牌結果；「對手接受報價的條件」與「對手的開局選點」照 standard 的公式估計，對人類玩家只是近似。

### 13.2 量測方法

- 實驗：每種設定 500 局（3–4 人）或 300–400 局（5–6 人），種子 20000 起，hard 依局數輪換座位，對手全為 standard。勝率的標準誤約 2 個百分點。
- 重複在同一批種子上調整會高估結果，所以最後另用沒調整過的種子 50000 起重測（§13.4）。
- `pnpm --filter @catan/bots bench 100 hard`：單一程序、種子 10000 起，記錄決策耗時。

### 13.3 演進與消融

| 步驟（累加） | 3 人 | 4 人 | 5 人 | 6 人 |
|---|---|---|---|---|
| 起點：hard 等於 standard（bench 200 局） | 30.0% | 26.5% | 20.5% | 12.5% |
| 學到的開局模型 | — | 27.0% | — | — |
| 國內交易 | — | 30.8% | — | — |
| 強盜、偷牌、騎士目標、壟斷 | 42.4% | 36.8% | 29.3% | 26.3% |
| 發展卡 1.3 倍 | 46.2% | 41.0% | — | — |
| 終盤搜尋、開局道路、牌池調整 | 45.0% | 42.4% | 38.0% | 24.8% |
| 積極打騎士 | 47.0% | 48.6% | — | 32.0% |
| 整理後的最終版本 | 46.6% | 49.0% | 42.5% | 31.5% |
| 公平份額 | 33.3% | 25% | 20% | 16.7% |

消融（在對應的階段，把 hard 的一部分換回 standard）：

| 換回 standard 的部分 | 4 人 | 3 人 |
|---|---|---|
| 開局放置 | 36.6% → 31.6% | 42.2% → 36.4% |
| 強盜、偷牌、騎士、壟斷 | 36.8% → 30.8% | — |

開局放置影響最大：在 standard 的起點上「永遠選第二好的點」，4 人局勝率從 25.6% 掉到 15.2%。

開局模型的資料：4 人局 standard 對局 3000 局，開局時 70% 的機率從 standard 評分的前 8 名中隨機挑選，記錄 12000 筆玩家開局的特徵與勝負，做 logistic 迴歸。5 折交叉驗證的對數概似 −0.539（只用常數項為 −0.562）。係數與特徵的定義在 `setup.ts`。

試過但沒有採用的做法：

- **以學到的局面評估做回合內搜尋**：在輕量模型上展開建造與交易序列，以 logistic 局面評估（104631 個回合結束前的局面）挑選序列。4 人局只有 21–24%，最大耗時超過 100 ms。原因是係數只反映相關性：手上的牌和發展卡被高估，又看不到「鋪路 → 幾回合後的聚落」的價值。最後只保留搜尋本身，用在終盤。
- 另外三份開局模型：較早的 1800 局資料、只用 3 人局的資料、只取 hard 座位的資料。都沒有比現行模型好。
- 以 standard 的公式精確模擬對手選點：差異在雜訊內，但保留，因為比原本的近似合理。
- 交易參數、強盜與威脅度權重、城市或聚落計畫的倍率：差異都在雜訊內。
- 列舉棄牌：差異在雜訊內，保留，因為不會比 standard 的貪婪丟法差。

### 13.4 結果與目標

沒調整過的種子（50000 起）：

| 人數 | 局數 | hard 勝率 | 目標（§2 H6） |
|---|---|---|---|
| 3 | 1000 | 47.5% ± 1.6 | ≥ 50%：**未達** |
| 4 | 1000 | 46.4% ± 1.6 | ≥ 40%：達成 |
| 5 | 600 | 38.3% ± 2.0 | ≥ 30%（公平份額 1.5 倍）：達成 |
| 6 | 600 | 31.7% ± 1.9 | ≥ 25%（公平份額 1.5 倍）：達成 |

bench（100 局、種子 10000 起、單一程序）：

| 設定 | hard 勝率 | hard 決策平均／最大 | 拒絕、卡死、看門狗、保底 |
|---|---|---|---|
| 3 人 1 hard 對 2 standard | 41% | 0.118／39.05 ms | 0 |
| 4 人 1 hard 對 3 standard | 38% | 0.121／6.57 ms | 0 |
| 5 人 1 hard 對 4 standard | 30% | 0.115／6.02 ms | 0 |
| 6 人 1 hard 對 5 standard | 28% | 0.115／12.84 ms | 0 |
| 3–6 人全 hard | — | 0.103–0.112／最大 34.98 ms | 0 |

bench 每種設定只有 100 局，勝率的標準誤約 5 個百分點；強度以上表的 1000 局為準。

終盤搜尋後來改為把建造花費退回模擬的銀行（與引擎的 `payBuild` 一致）。上面的種子 50000 起結果是修正後重測的（修正前 3 人局 46.7%、6 人局 30.3%，4、5 人局不變）。bench 的耗時在修正前、機器閒置時量測；修正後的勝率完全相同，而在 3–6 人各 25 局全 hard 對局的同一批局面上，修正前後展開的節點數也完全相同，所以沿用。

- 效能符合 §2 H5（平均 ≤ 5 ms、最大 ≤ 50 ms）。最大值出現在每個程序的第一個開局決策，含 JIT 暖機；單一程序連續 60 局 3 人局的最大值是 12.6 ms。
- 3 人局距離 50% 還差約 2.5 個百分點。§13.3 的參數掃描在 3 人局都停在 44–47%，再往上需要新的方法，例如更準確的開局評估。
