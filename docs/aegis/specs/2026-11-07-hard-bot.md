# 困難電腦（hard Bot）：規格與實作計畫

日期：2026-11-07。狀態：**使用者已批准方向與決策點，進入 PR 1（完整歷史＋計牌模組）。**

前置閱讀：`docs/SPEC.md` §4.9、§8.3；`docs/aegis/specs/2026-11-01-bot-opponents.md`（Bot 合約、不變式 I1–I9、BotDriver）。本文件是 hard 難度的設計與交付紀錄，權威需求仍以 SPEC 為準。相關 issue：#137（銀行精確存量會洩漏棄牌內容）。

## 1. 目標與範圍

在基本版（`base-2025`、`base-paired-2025`）新增 `hard` 難度：記性完美、會計牌，並且有前瞻規劃。

範圍內：

- 所有難度的 Bot 都會拿到自己座位投影過的**完整事件歷史**。目前伺服器只傳最近 40 筆，引擎快照最多保留 200 筆，而一局有 430–1000 筆事件。
- 歷史事件 API（`GET /api/games/:gameId/events`）改成與快照、推送相同的投影：只遮私有欄位，不再整筆省略事件。
- 計牌模組：只根據投影後的事件，推算每位對手的手牌分布、發展卡池與隱藏分數。
- hard 策略：開局前瞻、回合內搜尋、局面評估、依計牌結果決定強盜、偷牌、壟斷與交易、威脅與終盤判斷。
- 協定、伺服器、前端開放 `hard` 等級，並修訂 SPEC §4.9。

範圍外：

- 擴充版 profile 的 hard。hard 只支援沒有 rules module 的 profile；擴充版沿用 standard。
- 主執行緒上的蒙地卡羅整局推演（見 §7）、worker thread。
- Bot 的反報價、聊天。
- #137 的修正方式（另案）。

## 2. 已定案決策

| # | 決策 | 定案 | 理由 |
|---|---|---|---|

| H3 | 改進範圍 | 只放進 hard；standard／easy 行為凍結 | 難度之間的差距清楚；golden 測試（`test/golden/base-v040.json`）守住凍結 |

## 3. 資訊邊界

hard 可以使用的資訊，全部來自自己座位的 `GameView`（含 `events` 與 `hints`）、公開拓樸與規則常數：

| 來源 | hard 的用法 |
|---|---|
| 起始資源、擲骰產出、建造（含是否免費）、銀行／港口交易、完成的國內交易、豐收之年選的資源 | 精確加減對手手牌 |
| 壟斷（`taken` 只列出被拿走的玩家） | 被拿走的人該資源原本恰好是那個張數；沒列出的人原本是 0 張 |
| 偷牌：誰偷了誰 | 自己是小偷或受害者時知道牌面；否則把「受害者少一張、小偷多一張」分成各種可能 |
| 棄牌：誰棄了幾張 | 依超幾何分布展開各種可能；不讀銀行存量 |
| 公開的手牌張數、發展卡張數、已打出的騎士數 | 檢查推算是否一致、估算隱藏分數 |
| 牌庫組成（profile 的 `devDeck`）、牌庫剩餘張數 | 算出尚未現身的發展卡分布 |

hard 不得使用：

- 銀行存量的前後差（#137）；
- 其他座位的私有事件欄位（投影已經濾掉）；
- 任何 `GameState`。

SPEC §8.3 寫的「v1 不提供對手手牌推論助手」是針對玩家介面。hard 的推論只在策略內部使用，Bot 不聊天，也不會把推論結果傳給任何座位。

## 4. 現況評估（2026-11-07）

bench（每種設定 100 局，種子從 10000 起，master `0efd30c`）：

| 設定 | standard 勝率 | 公平份額 |
|---|---|---|
| 3 人：1 standard 對 2 easy | 39% | 33.3% |
| 4 人：1 standard 對 3 easy | 43% | 25% |
| 5／6 人：1 standard 對其餘 easy | 31%／31% | 20%／16.7% |

700 局全部正常結束，沒有拒絕或卡死。行動階段的一次決策約 0.07 ms。

standard 是每步只看眼前的無狀態啟發式。hard 要補強的地方（依預期影響排序；函式位置以 release 分支為準）：

1. **開局放置**（`src/base/setup.ts` 的 `setupSpotScore`）：只算點數、資源種類與港口。第二座缺木或缺磚各扣 3 分，等於不看盤面一律走鋪路擴張。hard：模擬蛇形順序中對手的選點並聯合規劃兩座；考慮數字分散、擴張潛力，依盤面選擴張或城市路線。
2. **回合內規劃**（`src/heuristic.ts` 的 `buildDecision`、`src/trade.ts` 的 `bankTradeToward`）：一次只看下一步，只有「換完這回合就能蓋」才交易。hard：搜尋本回合的交易、建造、發展卡序列，評估回合結束時的局面，含 7 點風險。
3. **局面評估**（`src/economy.ts` 的 `baseEconomyOf`）：`價值 / (1 + 預估輪數)`，權重不分階段；搶點只用距離打折，不看對手是否更快到達；最長道路只在差 1–2 條時才追，也不防守；發展卡價值固定。
4. **強盜與偷牌**（`src/base/robber.ts` 的 `robberCandidates`、`src/heuristic.ts` 的 `stealVictim`）：只看點數、領先程度與手牌張數。hard 依計牌結果，計算偷到的牌對自己的期望價值與對領先者的封鎖價值。
5. **壟斷**（`monopolyChoice`）：用產能比例估計；hard 直接用計牌結果。
6. **交易**（`src/trade.ts` 的 `acceptMargin`、`offerGain`、`proposeOffer`）：只看公開分數與自己的效用，只對全桌開價。hard 指名開價給確定有牌、又不構成威脅的玩家，並拒絕會讓對方立刻完成城市或聚落的交易。
7. **威脅與終盤**：沒有估算隱藏分數，除了騎士之外也不搜尋「這回合能否獲勝」。
8. **發展卡時機**（`knightDecision`、`devCardDecision`）：道路建設只要有合法道路就打，騎士只在少數條件下才打。
9. **棄牌與 7 點風險**（`discardDecision`、`handRelief`）：只保留第一順位計畫的牌，沒有計算擲出 7 的機率。

## 5. 架構

```text
game_events（完整、含私有欄位）
   │ listEvents(after) 補齊到 state.seq
   ▼
BotDriver runtime.history ──projectGame(state, botId, { events: history, hints })──▶ view.events（該座位的投影）
                                                                                     │
                                                    trackTable(view, selfId) ◀───────┘（純函式，只讀 view）
                                                         │
                                                    hard 策略（PR 2）
```

| 位置 | 內容 | PR |
|---|---|---|
| `packages/server/src/bot-driver.ts` | 每局快取完整事件；評估前從 `game_events` 補齊到 `state.seq`；投影時傳入完整歷史 | 1 |
| `packages/server/src/game.ts` | 事件 API 改用 `projectEvent` | 1 |
| `packages/bots/test/harness.ts` | 依狀態記錄完整歷史，`viewFor` 傳入；沒有紀錄的狀態退回 `state.log` | 1 |
| `packages/bots/src/tracker.ts`（新） | 計牌模組 | 1 |
| `packages/bots/src/hard/*`（新） | hard 策略 | 2 |
| `packages/bots/bench` | hard 設定、決策耗時 | 2 |
| `packages/bots/src/types.ts`、`packages/protocol`、`packages/web` i18n、`docs/SPEC.md` §4.9 | 開放 `hard` | 3 |

### 5.1 BotDriver 的歷史快取

- `GameRuntime.history: GameEvent[]`：持久化事件的純快取（含私有欄位），`forget()` 時一起丟棄。重啟後會從資料庫重新載入，「排程器不保存決策狀態」仍然成立。
- 每次 `evaluate` 讀到 `state` 後，從快取最後一筆的 seq 之後，每頁 500 筆向資料庫補齊到 `state.seq`，只收 `seq ≤ state.seq` 的事件。如果補完不連續或沒有補到 `state.seq`，丟掉快取，下次從頭載入；本次照樣決策，計牌模組會因為歷史不完整而降級。
- 投影仍透過 `projectGame` 的 `projectEvent` 遮掉私有欄位，與玩家的快照完全一致。

### 5.2 事件 API

`GameCoordinator.events` 改為 `events.map((event) => projectEvent(event, playerId))`：

- 旁觀者照樣看得到「誰偷了誰」「誰買了發展卡」，但看不到牌面；
- 收件人看得到私有欄位，回應中不含 `private` 物件。

這與快照、推送的行為相同，因此不會多揭露任何資訊。三個隱私測試原本寫死「旁觀者在歷史中看不到該事件」，改為「事件存在，但沒有私有欄位」。

## 6. 計牌模組（`src/tracker.ts`）

```ts
export function trackTable(view: GameView, selfId: string): TableBelief;

interface TableBelief {
  complete: boolean;                      // 歷史從 seq 1 連續到 view.seq，且 profile 沒有 rules module
  hands: Record<string, HandBelief>;      // 只有對手
  dev: DevCardBelief;
}
interface HandBelief {
  playerId: string;
  size: number;                           // 推算的張數，應等於公開 handSize
  worlds: { hand: Record<Resource, number>; p: number }[];  // 依機率遞減，同機率依 key 排序
  expected: Record<Resource, number>;
  min: Record<Resource, number>;          // 每種可能都至少有的張數（確定持有）
  max: Record<Resource, number>;
  exact: boolean;                         // 只剩一種可能
  consistent: boolean;                    // false 時 worlds 為空，expected 改用產能比例估計
}
interface DevCardBelief {
  unseen: Record<DevCardType, number>;    // 牌庫加上對手手上未打出的牌
  unseenTotal: number;
  players: Record<string, { held: number; bought: number; played: Partial<Record<DevCardType, number>>; victoryPoints: number }>;
}
```

演算法：

- 每位對手各自維護一組「可能手牌 → 機率」的集合，相同手牌合併。事件依 seq 順序處理（處理方式見 §3 的表），付出成本、壟斷時把不可能的手牌刪掉並重新正規化。
- **不知牌面的偷牌**：受害者的每種可能手牌依張數比例展開「少一張某資源」；被偷資源的分布再套到小偷身上，展開「多一張某資源」。小偷與受害者之間的相關性不保留，這是刻意的近似，但真實手牌仍一定留在可能集合中。
- **棄牌**：依多變量超幾何分布，展開所有「棄掉 n 張」的子集合。
- **上限**：每位對手最多保留 2000 種可能，超過時刪掉機率最低者（同機率依 key）。如果後續事件把所有可能都刪光（截斷刪到真實手牌，或歷史本身不一致），該玩家改標 `consistent: false`，只追蹤張數，分布改用產能比例估計。
- **完整性**：第一筆不是 seq 1、seq 不連續、最後一筆不是 `view.seq`、profile 有 rules module，或推算張數不等於公開 `handSize`，都會標成 `complete: false`。hard 遇到不完整時退回 standard 的估計方式。
- **發展卡**：`unseen` = profile 的牌庫 − 自己持有與打出的牌 − 對手打出的牌（騎士用公開的 `playedKnights`，其他從事件取得）。對手的隱藏分數期望值 = 持有張數 × `unseen.victoryPoint / unseenTotal`。
- **純函式**：只讀 `view`（不讀 `view.bank`）、不保留狀態、不使用亂數。實測每次決策重播完整歷史只要 0.3–0.5 ms（§11），所以不做跨呼叫快取。

## 7. 效能預算與量測

量測環境：4 人局、全部 standard 對局中的 146 個中盤狀態（2026-11-07）。

| 基本操作 | 單次成本 |
|---|---|
| standard 在行動階段的一次決策 | 0.07 ms |
| `actionHints`／`projectGame`＋hints | 0.03／0.035 ms |
| 引擎 `applyCommand`（深拷貝整份狀態，含 log 與統計） | 0.61 ms |
| Bot 自建輕量模型的複製（手牌、銀行、棋子） | 0.0005 ms |

以引擎展開本回合的交易與建造（重複局面只算一次）：

| 深度 | 平均節點 | 最大節點 | 平均耗時 | 最大耗時 |
|---|---|---|---|---|
| 1 | 4 | 17 | 3.4 ms | 18 ms |
| 2 | 14 | 146 | 15 ms | 177 ms |
| 3 | 31 | 650 | 45 ms | 1.2 s |
| 4 | 59 | 2231 | 107 ms | 4.6 s |
| 6 | 121 | 7665 | 307 ms | 23 s |

整局推演（所有座位用 standard）：1 輪 10.5 ms、2 輪 22.8 ms、到終局 159 ms。

結論：

- hard 的回合內搜尋必須用輕量模型，不能用引擎展開節點。
- 交易只往計畫需要的資源換、道路只朝目標方向鋪，用來修剪分支；節點上限約 800–1000，預估平均 2–5 ms、最壞 40–50 ms。
- 下一輪骰子直接算期望值，不實際模擬。
- 不在主執行緒上做蒙地卡羅推演。
- 計牌模組平均 0.3–0.5 ms、最大 4.3 ms（§11）。
